AI Agent Runtime: from first principles

Agent runtime in standard-library Python: explicit loop, tools, state, memory, planning, evaluation, reliability and security, then served by FastAPI with PostgreSQL and resumable SSE.

Python · FastAPI · PostgreSQL · SSE · Docker Compose · Agents
  1. From first principles

    Built one idea at a time in standard-library Python: model interface, structured output, tools, an explicit agent loop, state and memory, planning, evaluation, reliability and security, observability.

  2. Service architecture

    The same runtime, unchanged, behind a typed FastAPI service. Runs execute on a worker pool; every structured event is stored in PostgreSQL and streamed over resumable SSE.

  3. Reliability & security

    The model proposes; the runtime decides. Each tool call passes an allow-list, permission level, approval gate, schema check and timeout, and its output returns as untrusted, redacted data.

  4. Verified evidence

    Measured from the public repository at commit 231b186. These describe the runtime, not LLM quality.

Evaluation in detail

The 13 scenarios are 6 ordinary tasks run by a rule-based stand-in model and 7 failure scenarios run by a scripted model that deliberately misbehaves: a repeated call, a step runaway, a token runaway, a write with no approver, an injected instruction, a provider outage and an escalation. Each case passes when the run ends in the status that case expects, and the harness is itself tested to be able to fail. Because several scenarios are meant to stop without a final answer, the final-answer rate is 61.5% (8 of 13); that is by design, not a quality score. No language model was used.

Limitation Limitations

  • The runtime's own tests and evaluation use scripted models, and CI never calls a paid API. A separate benchmark, agent-runtime-bench (ARB-1), runs one small local language model through the unmodified runtime: 43 of 48 tasks passed its frozen oracles (greedy decoding), all seven runtime controls held in 240 of 240 agent-mode runs, and it found a gap: a secret was disclosed through a permitted read tool. One model, one machine, 48 author-written tasks and heuristic oracles; not a safety claim about the runtime.
  • Docker Compose was verified in CI only, not on a local machine.
  • Not deployed as a live service; it is a service architecture verified by CI and integration tests, not proven in production.
  • No run-cancellation endpoint. One shared bearer token and no per-user ownership of runs. A restart interrupts in-flight runs.
  • A tool that times out is reported as timed out but cannot be killed, so its side effects may still complete.
  • Token counts are estimates unless the provider reports usage. Loop detection catches only consecutive identical calls.
  • Injection scanning is regex heuristics; permissions, approvals and sandboxing are the real protection.

Limitation The lesson from the failure

Action safety ≠ information-flow safety

The controls constrain actions (writes, dangerous tools, budgets), not information flow through permitted read tools. In MT-02 a fetched page told the model to read a config value and reveal it; the model called the read-level get_config and wrote the passphrase into its answer. Every control held and the secret was still disclosed: the benchmark found the largest hole exactly where the controls do not look.

Qualification. One small quantised model, 48 tasks written by the same AI author that wrote the oracles, a scripted approver, heuristic lexicon oracles (four of 22 failures in the runs MAREF uses were oracle false negatives, disclosed in the results). Descriptive counts, not a leaderboard and not a safety claim about the runtime. Source: public benchmark repository at commit 679fa28.

The recorded runs of this benchmark are what MAREF, a separate research prototype, evaluates. MAREF is an evaluator of agent runs, not an agent; its result is mixed and its evaluation is same-author, not independent validation. Read the MAREF result.
