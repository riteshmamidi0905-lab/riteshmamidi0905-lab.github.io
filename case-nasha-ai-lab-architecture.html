NASHA AI Lab: Architecture and an Honest Evaluation

An evaluation-first design for AI in business operations, built around a proposed brewery and reported with its failures.

01 / THE PROBLEM

Why it exists

Can a language model explain an operations gap (for example, expected stock against counted stock) using only verified facts, abstain when the facts are missing or conflicting, and ignore text that tries to instruct it, and how would we know? NASHA, a proposed Indo-Mex brewery, is the business scenario. It is a concept: no customers, suppliers or revenue.

Text version of the architecture
  1. Facts first. The business facts are a trusted snapshot. Text such as an entity's alias is data, never an instruction.
  2. The model only proposes. The model's output is a structured set of claims. Nothing it writes is shown unless every claim verifies.
  3. A strict validator. Each number, unit and fact reference is checked; abstention with exactly the right reasons is a correct answer.
  4. The server writes the explanation. What a person reads is rendered by code from the verified facts, not copied from the model.
  5. Gates were written before the run. Acceptance thresholds, the 60-case set and an independent scorer were fixed in advance and are not changed after seeing results.

03 / IMPLEMENTATION

What was built

  • Validator and renderer with 60 official cases, a diagnostic set and an independent scorer.
  • Paired diagnostic experiment comparing two prompts on 21 pinned cases, implemented and tested offline (not yet run against a model).
  • Evidence handling with a hash-chained ledger, single-use approvals and secret scanning of exported evidence; these controls went through four rounds of independent AI-assisted review.

04 / ENGINEERING DECISIONS

Choices and trade-offs

  • Pre-register the gates. Thresholds are not lowered to make a model pass.
  • Separate generation, validation and scoring. The scorer is independent of the code under test.
  • Publish the failure. A strict, failing evaluation with a clear cause is more useful than a demo with no evidence.

07 / LIMITATIONS

What this does not show

  • Live evaluation not passed. The model has not met its acceptance criteria.
  • A candidate prompt fix exists and has not been tested against a model; the paired GPU re-run is planned and has not been run.
  • Passing 953 offline tests shows the harness and controls behave as tested; it is not model capability or production readiness.
  • Not deployed; the brewery is a business concept, not an operating business; the review was AI-assisted, not a formal external audit.

08 / BUSINESS RELEVANCE

Where it matters

Any operations team considering AI explanations (inventory, supplier, finance) needs the same discipline: define the contract, verify every claim against facts, measure honestly, and keep a person in the loop.
