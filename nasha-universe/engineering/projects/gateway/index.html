    Architecture

    Business problem

    A simulated supplier can accept a request and then return an error. Creating another intent after that ambiguous result risks duplicate action.

    Customer requirements

    • Authenticate both API access and the configured supplier connection.
    • Validate payloads and bind a stable idempotency key to tenant/run.
    • Bound retries and preserve uncertain outcomes.
    • Recover a persisted receipt and make completed replay a local no-op.

    Architecture decision

    Put durable intent before transport, and require receiver idempotency. More retries alone cannot solve an ambiguous external outcome.

    Implementation

    SupplierClient accepts only a literal loopback origin, disables redirects, applies a timeout and makes at most three HTTP attempts. The separately running supplier stores key/payload digests and receipts. A changed payload under the same key conflicts. The platform records every attempt and stores the recovered receipt.

    Technologies

    • Python
    • HTTPX
    • Authenticated REST
    • Pydantic
    • SQLite
    • Idempotency
    • Bounded backoff

    Security

    Callers cannot choose arbitrary destinations. Only approved persisted proposals can dispatch. Terminal errors and malformed receipts fail closed. The transport is local HTTP and the supplier is an explicit test double, not SAP or a live enterprise system.

    Evaluation methodology

    Unit tests inject retryable/terminal responses, timeouts, invalid receipts and payload conflicts. The actual HTTP demonstration injects two pre-accept failures and a failure after the supplier commits success.

    Test evidence

    • test_http_retries_and_receipt_persistence
    • test_http_fatal_errors_do_not_retry
    • test_http_uncertain_failure_preserves_intent
    • test_supplier_auth_idempotency_and_lost_response
    • test_malformed_supplier_response_fails_without_receipt

    Measured local results

    • Actual loopback HTTP attempt sequence: 503 → 503 → 503 → 200.
    • The supplier accepts exactly one synthetic order.
    • The same-key retry recovers the existing receipt.
    • Subsequent dispatch issues zero HTTP requests; the audit chain verifies.

    Limitations

    Depends on the receiver’s idempotency contract. No live enterprise credentials, generalized provider reconciliation, durable retry scheduler or production TLS configuration.

    Business value

    Demonstrates how to avoid duplicate consequential actions under uncertain transport outcomes. Production value would be measured through duplicate-action rate and reconciliation workload, not assumed financial savings.

    The private engineering package includes executable code, deterministic fixtures, demo commands and transcripts. Public source for this local extension has not been released. This page does not claim that a separate upstream repository is its implementation.
