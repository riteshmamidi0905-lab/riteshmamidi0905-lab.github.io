    Architecture

    Business problem

    A simulated implementation team needs evidence that a bad local configuration cannot be accepted as a healthy release, and that a consistent checkpoint can be restored safely.

    Customer requirements

    • Separate liveness from readiness and expose operational counters.
    • Create a consistent SQLite checkpoint and hashed file inventory.
    • Reject tampered releases and existing restore destinations.
    • Exercise failure and rollback using actual local processes.

    Architecture decision

    Verify readiness and checkpoint integrity before calling a rollout successful. Preserve the failed candidate and restore into a new path rather than overwriting a user database.

    Implementation

    The lab snapshots code, UI, configuration and SQLite backup. Checkpoints are finalized in DELETE journal mode before hashing. Readiness checks database integrity and the audit chain. A deliberately unhealthy candidate is rejected; the prior verified configuration starts with its restored checkpoint.

    Technologies

    • Python
    • Uvicorn
    • SQLite backup API
    • SHA-256 inventories
    • Health/readiness
    • Structured logs
    • Local subprocesses

    Security

    Restore refuses existing paths and release verification rejects changed inventories or digests. Manifests are trusted local inputs, not signed attestations. Existing Pages/rollback approval gates remain binding.

    Evaluation methodology

    Tests cover tampered configuration, no-overwrite restore, audit-corruption readiness failure and real process rollback. The inherited release suite uses its original real Ruby/Psych parser and unchanged negative controls.

    Measured local results

    • Readiness: healthy 200 → injected candidate 503 → restored release-a 200.
    • Restored synthetic sales remain 17,200 cents.
    • A WAL-sidecar inventory defect was caught and fixed by regression tests.
    • Inherited gates: 152 workflow-safety, 115 release-evidence and 19 rollback-guard checks pass locally.

    Limitations

    Local configuration/checkpoint rehearsal only; no public/cloud deployment, zero-downtime guarantee, signed supply chain, arbitrary schema downgrade or production disaster-recovery claim.

    Business value

    Makes release acceptance and recovery evidence reviewable. A real implementation should define RTO/RPO and rehearse against those objectives; no production uptime or MTTR improvement is claimed.
