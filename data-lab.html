03 / DATA ENGINEERING

Ingest, model, gate, publish

The warehouse pipeline generates a synthetic enterprise source, loads it in partitions under data contracts, builds 7 layers of plain SQL models with recorded lineage (203 edges), runs blocking and warning quality gates, and only then marks the warehouse published. A raw-gate failure skips the rebuild and keeps the previous published content.

  • Result: published, 0 blocking failures, 1 warning in 0.5 s, 47 tables.
  • Error handling: a load interrupted after one partition raised an error; resuming completed and the data tables matched a clean run (only the run-history table differs, by design).
  • Gate finding: labor % of sales below 0.6, observed 4.0075 (limit < 0.6): the synthetic labor figure is implausible, so the gate warns and does not block. That is a data-realism finding about the generator, not a business result.
  • Not implemented: dbt, Airflow or any scheduler. Of the 100 sampled postings, dbt appears in 15 (3 require it) and Airflow in 8 (3 require it), mostly as preferred. They would add moderate evidence for analytics-engineer roles, not for analyst roles; they are a later step.

A/B test: did the injected effect get recovered?

341 guests (176 treated, 165 control); sample-ratio check p = 0.55 (no imbalance detected); minimum detectable effect about 0.53 units per guest. Primary metric: extra units of one appetizer per guest. The true injected effect is 0.226.

A/B estimates
EstimatorEstimateStd. error95% intervalp-value
Unadjusted0.2820.138[0.012, 0.552]0.041
CUPED0.3010.135[0.037, 0.566]0.026
Post-stratified0.3000.139[0.027, 0.572]0.031

Interpretation. All three estimators put the effect near 0.30 units per guest and their intervals contain the injected truth; covariate adjustment (CUPED) narrows the interval only slightly because the pre-period correlation is weak (0.20). Over 1,000 simulated repeats the adjusted analysis has near-nominal coverage and rejects a true null 4.6% of the time, but detects this effect only 39% of the time at this sample size. Recommendation the data supports: the analysis method is sound on this simulation; a real test of a menu change would need more guests than 341 to be conclusive. It does not show that any real change helps the business.

  • Randomisation is simulated; the 'effect' is whatever the injection code says. Recovering it proves the ANALYSIS is unbiased on this data-generating process, not that any real menu change works.
  • No guests exist: guest ids come from a seeded assignment process (config.GUEST_*). Real repeat-visit dynamics, interference between guests at one table, novelty effects and seasonality are absent.
  • The effect is on a single appetizer count; cannibalisation, margin and long-run retention are not modelled, so the experiment cannot say whether the change is good for the business.
  • Only 4 weeks and a few hundred guests: heavy tails, repeated visits per guest and new guests arriving after assignment are handled crudely (new guests have a pre-period covariate of zero).
  • Monte Carlo coverage is relative to the finite-population truth of this guest panel (fixed baseline behaviour, random assignment and injection), i.e. randomisation inference, not a superpopulation claim.
  • Same author wrote the injection and the analysis (no independent review).

08 / REPRODUCIBILITY FINDING

14 of 15 files identical; the 15th differs by about 5e-16

14 of 15 regenerated result files are byte-identical; the 15th (experiment.json) matches to within 5e-16 on 10 floating-point values. Byte-for-byte identity across all files is NOT demonstrated.

Cause (evidence-based): Floating-point summation order inside np.cov (used for the CUPED regression coefficient theta); platform- and library-dependent last-bit differences. Not serialization, not data order, not nondeterminism.

  • Same Python process, same inputs, run twice: identical output.
  • Every differing value is on the CUPED path (theta and the estimate/CI derived from it); all unadjusted, stratified, p-value and count fields match exactly in all four environments tested.
  • Four environments each differ from the committed file by 4.4e-16 to 5.0e-16 (10 to 12 values): Python 3.14.5 / numpy 2.5.4 / scipy 1.18.1; Python 3.12.16 with numpy 2.5.4 / scipy 1.18.1; numpy 2.1.3 / scipy 1.14.1; numpy 1.26.4 / scipy 1.13.1 (all macOS arm64). None reproduces the committed bytes, so the original platform or BLAS build is the likely source; that was not tested.

11 / LIMITATIONS

Read this before quoting any number

  • All data is synthetic and generated by the author; results describe the generators, not a business or a market.
  • The analytics and the warehouse were written by the same author and are tested by the author's own tests; this is not an independent audit.
  • The SQL library runs on SQLite; the warehouse also has a tested PostgreSQL variant. No cloud warehouse was used.
  • No dbt, Airflow, Tableau, Looker, Power BI or Salesforce evidence is claimed.
  • Twelve tests are skipped by design (private answer keys); their subject is unverified here.
  • The live model evaluation of the NASHA AI Lab has not met its acceptance criteria (failed); this lab does not change that.
