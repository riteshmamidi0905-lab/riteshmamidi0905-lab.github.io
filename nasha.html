Flagship case study · independent engineering

A governed AI operations platform, tested where it breaks.

NASHA is a proposed restaurant-and-brewery concept. It is not an operating business, it has no customers, and every order, supplier and number below is synthetic. It exists to give an engineering system a realistic job: notice that stock disappeared faster than the recipes explain, propose a purchase, and make sure a human, not the model, decides.

What is real

The code, the tests, the recorded runs on this page and the numbers measured when the evidence was exported.

What is synthetic

Orders, inventory counts, supplier quotes, prices, anomalies and people. None of it is a business result.

What is not claimed

No production deployment, no real-model run, no security certification, and no live demo: this page replays recorded evidence.

        Security design

        Four layers, each sufficient on its own.

        An unauthorised purchase has to get past all four. The tests try each, and the schema makes “sent” unrepresentable.

        1 · Identity and tenant

        Each tenant has its own signing secret, warehouse, ledger, approval store and memory. A token from another tenant fails signature verification; the same location id resolves to different data per tenant.

        2 · THE WEIR policy

        A default-deny policy per role. The quality-lead role has no procurement tool at all, so the call is blocked before anything runs and no approval is even requested. Supplier-written text is labelled untrusted.

        3 · Human approval, bound to the call

        The write is held for a different, authorised person. The approval is bound to the exact call, expires, and works once. Changing the quantity, supplier, quote or amount after approval needs a new approval.

        4 · Upstream and schema

        The procurement upstream re-validates against the ledger and the warehouse; the ledger’s only order state is DRAFT_NOT_SENT, writes are idempotent, and the audit trail is hash-chained so edits are detectable.

        Found by a regression test while building this: the estimated cost was not part of the approved call, so a tampered cost could pass. It is now bound and re-checked.

            Limits

            What this does not show.

            • BlockedThe real-model integration test cannot run here: there is no local model runtime, and downloads are blocked. The model planner is verified only with scripted clients.
            • Not integratedMy Production AI Agent Platform is a separate repository. NASHA reuses ideas and adapted code from it; it does not import or run on it.
            • Architectural onlyTenants share one process and code, plus the reference recipe files used to seed each scenario. There is no per-tenant recipe versioning.
            • SyntheticSales, prices, quotes and anomalies are generated. The variance detector was scored against three injected anomalies, a small sample.
            • LocalThe evidence comes from local commits that have not been pushed.
