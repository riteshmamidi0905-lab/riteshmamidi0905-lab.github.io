        Engineering investigation

        Preventing audit-chain corruption under concurrent requests.

        A full test run reported a pass, and also three dead worker threads. The warning was an audit-record write failing under concurrency. This is what it was, why the test had missed it, and what changed.

        Loading recorded results…

        Engineering detail: error, root cause, test, fix, limits

        Discovery. Not by an assertion. The suite at commit cb4ae79 passed, and pytest also reported three unhandled thread exceptions in the lead-conversion race test.

        PostgreSQL error. psycopg.errors.UniqueViolation: duplicate key value violates unique constraint "audit_log_pkey", raised from the audit write that records a refusal.

        Root cause. pg_advisory_xact_lock is held until the end of the transaction. The success path ran inside one; the refusal path ran in autocommit, where every statement is its own transaction, so the lock was released before the head was read. Product defect, timing-dependent.

        Why the test missed it. It asserted one winner and one opportunity row. The losing threads died inside the worker, never reached the result list, and pytest reported them only as warnings.

        Fix. _audit now executes the lock, the read and the insert inside with self.con.transaction():. No assertion, privilege or release requirement was relaxed.

        with self.con.transaction():
    self.con.execute("SELECT pg_advisory_xact_lock(...)", ("audit:" + tenant,))
    last = self.con.execute("SELECT seq, hash FROM audit_log WHERE tenant_id=%s ORDER BY seq DESC LIMIT 1", ...)
    ...  # compute next seq and hash, then INSERT INTO audit_log

        Regression tests. Worker exceptions are re-raised in the caller; 16 concurrent refusals must produce exactly 16 deny rows with unique, contiguous sequence numbers; a five-round mixed storm of allows, denials and a conversion race; a rollback test; and a deterministic test that pauses one writer between the read and the insert and observes the other waiting on the lock.

        Limits. One PostgreSQL instance and one process; no multi-node or failover claim; the pre-fix behaviour is reproduced by a test plugin, not by the historic commit; no throughput or latency measurement was made. The hash chain makes tampering detectable, not impossible.
