Growth OS: building a governed AI business platform.

One workflow, taken all the way through: a synthetic sales lead is qualified with evidence, the write to the CRM is held by THE WEIR, a different person approves that exact action, the CRM changes, and the audit log can prove who did what. It runs on PostgreSQL with row-level security, behind an HTTP API and a real web interface. The platform is industry-agnostic: it is exercised here on two synthetic tenants, NASHA — Flagship Hospitality Launch Case Study (a proposed brand, not an operating business) and Meridian Fitness, a second business with different products, prices and people. Every tenant, customer and number is synthetic, nothing is deployed, and no one is ever emailed.

    Architecture

    Five layers, each one enforced rather than described.

    An action has to pass every layer. Removing any single one is covered by a mutation test that shows the next layer still stops it, or that the probe notices.

    1. 01 · BUILTPostgreSQL: tenant boundary

      Composite tenant keys and foreign keys, row-level security forced on every table, default deny, a non-privileged login role, append-only audit privileges, a stage-rule trigger.

    2. 02 · BUILTService layer: role policy and rules

      Default-deny actions per role, every denial audited, consent and suppression rules, optimistic lead versions, no send or publish method.

    3. 03 · BUILTTHE WEIR: approval for the one consequential write

      The same gateway as my separate mcp-weir project holds crm__apply_lead_qualification until a different, authorised person approves that exact call (bound to session and call hash, with a time limit and single use). No second authorization framework exists.

    4. 04 · BUILTHTTP API and web interface

      Tenant comes only from the path; sessions are tenant-bound; one error envelope; idempotency keys; pagination; correlation ids; a contract test; six screens backed by that API.

    5. 05 · MINIMALProduction AI Agent Platform: tool layer only

      Three read-only Growth OS tools run through its tool and risk contract with a refusing approval broker. Its planner, models, retrieval and approval broker are not used, and the qualification workflow is deterministic rules, not an agent. No claim of fuller integration.

    Mutation tests

    Remove a control and the probes must notice.

    Ten mutants delete one database or service control each. Eight more break the workflow itself: authorization, tenant isolation, the qualification threshold, suppression, consent, approval single-use, the CRM state check, and the audit write.

        Pipeline rules

        The stage machine lives in the database.

        A trigger checks every stage change against a rules table, so no application bug and no direct SQL can skip a stage. All 30 stage pairs were attempted against PostgreSQL and recorded.

          Tenant isolation

          Probed on every table, recorded.

          Two synthetic tenants with different products, prices, segments and customers. Tenant A looked for tenant B’s rows by tenant and by id; a session with no tenant set looked at everything.

          Privileged actions the application role attempted

            Limits: one database and one process serve both tenants (logical, not physical isolation); the embedded test server uses trust authentication; no encryption-at-rest or key management; no external penetration test. Two working synthetic tenants do not make this a commercial SaaS.

            Honest limits

            What this is not.

            • SyntheticAll data is generated. There are no customers, no transactions and no production deployment; the demo runs on localhost with development passcodes.
            • Not builtNo email, ad or publishing integration, by design: outbound communication is unrepresentable in the schema and API. Twelve of the 25 capabilities are not started.
            • SimulatedLead scoring and segmentation are transparent rules over synthetic data, not validated models; pricing elasticity is an assumed input.
            • UnverifiedThe overall release gate stays at REQUIRES_REVIEW until a real model-runtime test executes, and the remote CI has not been run. This page claims neither.
