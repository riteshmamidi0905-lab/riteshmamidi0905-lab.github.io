NASHA Growth OS · working name · foundation phase

A growth platform where the database says no.

An AI-powered business growth platform has to be trustworthy before it is clever. This case study shows the foundation I built first: one shared, tenant-aware data model on PostgreSQL, a CRM and pricing core, and controls that hold even if the application code is wrong. NASHA is a proposed business; every tenant, customer and number here is synthetic, and the platform has no customers.

Of the 25 planned business capabilities, only the ones marked tested have automated evidence, and none is marked integrated: there is no product interface yet. Percentages are deliberately not shown.

Architecture

Four layers; two are built.

The database and the service layer are implemented and tested. THE WEIR approval for consequential actions and the agent runtime come next; they are shown as designed, not claimed.

  1. 01 · BUILTPostgreSQL: tenant boundary

    Composite tenant keys and foreign keys, row-level security forced on every table, default deny, a non-privileged login role, append-only audit privileges.

  2. 02 · BUILTService layer: role policy and rules

    Default-deny actions per role, every denial audited, consent and suppression rules, stage rules, no send or publish method.

  3. 03 · DESIGNEDTHE WEIR: approval for consequential actions

    The existing gateway holds writes with outside effects for a different person to approve. Not yet wired to Growth OS.

  4. 04 · DESIGNEDAgents on the Production AI Agent Platform

    Read and analysis tools registered through its tool and risk contract; consequential tools never registered there.

Pipeline rules

The stage machine lives in the database.

A trigger checks every stage change against a rules table, so no application bug and no direct SQL can skip a stage. All 30 stage pairs were attempted against PostgreSQL and recorded.

    Tenant isolation

    Probed on every table, recorded.

    Two synthetic tenants with different products, prices, segments and customers. Tenant A looked for tenant B’s rows by tenant and by id; a session with no tenant set looked at everything.

    Privileged actions the application role attempted

      Limits: one database and one process serve both tenants (logical, not physical isolation); the embedded test server uses trust authentication; no encryption-at-rest or key management; no external penetration test. Two working synthetic tenants do not make this a commercial SaaS.

      Control mutants

      Remove a control and the probes must notice.

      Each mutant deletes one protection: row-level security, a foreign key, the stage trigger, a policy entry, the consent check, audit of denials, a state constraint, the synthetic-email rule or the audit privilege.

        Not built yet

        What this foundation does not do.

        • Not builtNo product interface, no HTTP API, no workflow registry, no agents inside Growth OS yet.
        • Not builtNo email, ad or publishing integration, by design: outbound communication stays disabled and unrepresentable until explicitly authorised.
        • SimulatedLead scoring and segmentation are transparent rules over synthetic data, not validated models; pricing elasticity is an assumed input.
        • NextWire a first workflow (lead qualification) through the governed approval path, then the interface.
