Evaluate model outputs with repeatable rubrics, hard gates, and inspectable failure cases.

LLM Eval · LLM-as-Judge · FastAPI · Dashboard
  1. Test cases

    JSONL cases carry a prompt, context, output and reference. An 18-case benchmark ships with the repo.

  2. Model outputs

    The evaluator scores outputs you supply. It calls a model only if you enable a judge.

  3. Rubric judge

    A JSON or YAML rubric: weighted criteria, optional hard thresholds, 14 metrics, and an optional chat(prompt) judge.

  4. Scores

    A weighted per-case score plus pass/fail. A threshold can fail a case even when its weighted score is high.

  5. Dashboard

    A self-contained HTML dashboard, a JSON report, a REST API and a CLI --fail-under gate for CI.

What it is
llmeval: a rubric-driven platform for scoring LLM outputs. It pairs 14 deterministic offline metrics with an optional LLM-as-judge backend.
How it works
Cases go through a rubric of weighted criteria. Metrics or judges score each criterion. The result is a per-case breakdown, a JSON report, an HTML dashboard and a CLI gate.
Engineering decisions
Weighted scores and hard thresholds are separate on purpose. A high overall score cannot override a required safety or grounding check.
Tradeoffs
Deterministic metrics are reproducible and need no API key. Optional judges can score nuanced criteria but need calibration and human review.
Limitations
Token-overlap faithfulness is a heuristic. Neither metrics nor judges prove factual reliability on their own.
Evaluation
An 18-case RAG-QA benchmark ships with the repository, plus tests for deterministic scoring, thresholds, the API and the reports. The CLI has a fail-under option for CI.
What I would build next
Track agreement between the judge and human reviewers, so the judge itself can be trusted.

Flagship 03 · AI reliability · MAREF research prototype

Reliability needs more than one score.

Explanatory visualization of six of MAREF's eight dimensions · not the measured results
  1. The problem

    An agent can finish a task, sound confident and still be wrong. One average score hides which way it failed.

  2. Task Accuracy

    Is the answer correct? Compare the response with a task-specific reference or a deterministic check.

  3. Groundedness

    Can each claim be traced to evidence? A citation only counts if the source actually supports the claim.

  4. Hallucination Resistance

    Does the agent avoid unsupported information? Invented figures and names are the signal.

  5. Instruction Adherence

    Did it follow the constraints: format, length, required content, no spurious refusal?

  6. Consistency

    Does the same task give stable answers across runs? Variance is a reliability failure of its own.

  7. Task Completion

    Did the workflow actually do the job? Skipped steps and missing tool calls count.

  8. No scores here

    This scene is an illustration and shows no measured results. MAREF's measured results, with their denominators and caveats, are in the full evaluation.

MAREF: Multi-Dimensional Agent Reliability Evaluation Framework

Evaluating the Reliability of Large Language Model Agents: A Multi-Metric Framework for Accuracy, Hallucination, Consistency, and Task Completion.

Abstract. An agent can answer correctly and still be unreliable: ungrounded, inconsistent, or unfinished. MAREF evaluates a whole agent run (its tool calls, side effects and ending, not only the final text) on eight dimensions so each failure mode can be inspected on its own instead of being averaged into one score. The explorer below walks through six of them with illustrative examples; the other two are action correctness and policy and injection safety. The measured result is in the card above.
