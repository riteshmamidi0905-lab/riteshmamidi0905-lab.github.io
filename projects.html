Supporting · AI systems

From task to evaluated action.

Real agent loop and real retrieval · fixed sample corpus · no language model
  1. Objective

    An objective arrives in plain language: “Convert 5 km to mi, then multiply by 2.” Everything downstream depends on reading it correctly.

  2. Planning

    The planner decides what kind of problem this is: a single lookup, or a composition where one tool’s output feeds the next.

  3. Tools

    It chooses from four tools: a calculator, a unit converter, a tiny knowledge base and text statistics. The calculator walks a restricted syntax tree and never calls eval.

  4. Retrieval

    Fact questions go to a knowledge base that matches on keyword overlap. When nothing matches, the answer is “unknown” instead of a guess.

  5. Execution

    The first observation, 3.107 mi, flows into the second step. That is real ReAct feedback: the second action depends on the first result.

  6. Evaluation

    Then the trace is checked: did it finish, did any tool error, does the second number re-derive from the first?

  7. Result

    Only then does the agent answer. In the lab below, this same loop runs in your browser on any task you type.

  8. Question

    The same discipline applies to retrieval. A question arrives and is embedded as a vector: 1,024 signed hashed dimensions, no model download.

  9. Chunks

    The fixed sample corpus is cut into sentence-aware chunks. These eight, each with a document id, are everything retrieval can see.

  10. Retrieval

    Cosine similarity and keyword overlap are fused (0.7 vector, 0.3 keyword) and the chunks reorder. The top four go forward; the rest fall away.

  11. Citations

    The extractive reader quotes the best sentences from the top chunks and cites them. If nothing overlaps the question, it abstains instead of guessing.

Real-Time Streaming Pipeline

Detect fraud on a live event stream — without waiting for a nightly batch.

Kafka · Spark Structured Streaming · Cassandra · Docker
  1. Synthetic events

    producer.py emits transactions at a configurable rate. About 3% are crafted to trip the fraud rules.

  2. Kafka

    Durable ingestion. Each transaction is keyed by account ID.

  3. Fraud rules + windows

    flag_fraud: amount over 2,000, a high-risk country, or a non-positive amount. One-minute tumbling windows with a two-minute watermark.

  4. Cassandra

    Two sinks: per-transaction verdicts and per-merchant window metrics, each with its own checkpoint.

01 / 04Synthetic events

producer.py emits transactions at a configurable rate. About 3% are crafted to trip the fraud rules.

Ritesh explains

Fraud signals decay in minutes. I used explainable rules so every flag can be inspected, and event-time windows with a watermark so late data cannot grow state forever.

What it is
A runnable fraud-detection stream: Kafka, Spark Structured Streaming and Cassandra in one Docker Compose stack, fed by a synthetic transaction producer.
How it works
The producer writes events to Kafka. Spark parses the JSON, flags fraud with rules, and aggregates one-minute merchant windows. Two Cassandra tables store verdicts and metrics.
Engineering decisions
Explainable rules make every fraud flag inspectable. Event-time windows and a watermark bound how much late-data state Spark has to keep. Separate checkpoints track each sink.
Tradeoffs
Rules can be read and debugged but cannot learn new patterns. A watermark keeps state bounded but drops events that arrive too late.
Limitations
The transactions are synthetic and detection is rule-based. This is not a deployed payment-risk model.
Evaluation
The Spark transforms are pure functions tested on static DataFrames: JSON parsing, fraud-rule decisions, event-time merchant aggregation. The full Kafka and Cassandra runtime is a separate integration check.
What I would build next
Test sink idempotency under failure and restart, reviewing checkpoints and Cassandra keys together.

Spark Data Lakehouse

Turn 300K+ raw events into clean, query-ready marts with a medallion architecture.

PySpark · Parquet · AQE · Medallion
  1. Raw events

    Synthetic input events processed with local Spark.

  2. Bronze

    The ingestion layer: the raw record of what arrived.

  3. Silver

    Cleaning, deterministic deduplication and enrichment, using broadcast joins for small dimensions.

  4. Gold marts

    Business aggregates written as partitioned Parquet.

  5. BI / SQL

    The gold marts are shaped for BI and SQL. Data-quality rules guard each layer boundary.

01 / 05Raw events

Synthetic input events processed with local Spark.

Ritesh explains

Bad rows should fail loudly between layers, not surface in a dashboard. Each medallion layer has one job, and quality checks sit at the boundaries.

What it is
A medallion-style Spark lakehouse: Bronze, Silver and Gold layers with data-quality checks between them.
How it works
Each layer has one job: ingest, then clean, deduplicate and enrich, then aggregate into business marts that are written as partitioned Parquet.
Engineering decisions
Small dimensions use broadcast joins. Partitioned Parquet and Adaptive Query Execution target avoidable shuffle and scan work.
Tradeoffs
Gates between layers fail loudly when inputs drift, instead of letting bad rows flow into the marts.
Limitations
Local Spark and synthetic inputs demonstrate the processing architecture. They do not demonstrate production scale.
Evaluation
Unit tests cover cleaning, deterministic deduplication, enrichment and the gold aggregates. Quality rules inspect nulls, negative quantities and invalid enum values.
What I would build next
Turn the quality checks into an explicit contract per layer, and deduplicate as early as possible.

Supporting build 03 · GenAI · LLM

GenAI Document Assistant

Answer questions from your own documents — grounded, cited, and streamed.

RAG · FastAPI · SSE · pgvector
  1. Query

    A FastAPI backend with a browser chat interface. A router-agent decides when to search and when to answer.

  2. Retriever

    Cosine search over hashed embeddings (or sentence-transformers), then a 0.7 vector plus 0.3 keyword re-rank.

  3. Relevant chunks

    Sentence-aware chunks of about 480 characters with one sentence of overlap.

  4. LLM

    By default an offline extractive reader that answers only from context and abstains otherwise. Ollama, Gemini and OpenAI backends are configurable.

  5. Cited answer

    Answers carry [n] citations back to chunk IDs, and responses stream token by token.

01 / 05Query

A FastAPI backend with a browser chat interface. A router-agent decides when to search and when to answer.

Ritesh explains

A fluent answer is not enough; it needs a path back to its source. The default reader is extractive, so it can only quote what was retrieved, and it abstains otherwise.

What it is
A full-stack assistant that answers from your own documents, with citations back to the source chunks.
How it works
A router decides whether to search or answer. Documents become sentence-aware chunks, retrieval blends vector similarity with keyword overlap, and the reader answers only from what was retrieved.
Engineering decisions
An offline extractive reader keeps the default path reproducible with no credentials. Embedding, vector store and generation backends switch by configuration.
Tradeoffs
Feature hashing works offline but is weaker than semantic embeddings. The extractive reader never invents, but it cannot paraphrase.
Limitations
Sample-corpus evaluation and local load tests do not show performance on arbitrary documents or live users.
Evaluation
A sample-corpus harness checks retrieval hit-rate, reciprocal rank, faithfulness and answer relevance, with CI thresholds. Tests cover retrieval, routing, streaming and the API.
What I would build next
Test retrieval failures on a broader corpus, and measure how well the system abstains.

01 / 05Feature store

The model bundle keeps the scaler and feature view together with the model.

Ritesh explains

Models get trained once and forgotten. Registry stages and PSI/KS drift checks keep the model's lifecycle and its inputs visible.

What it is
A local end-to-end model lifecycle: train candidates, register a model, promote a version, serve predictions and monitor drift.
How it works
Experiment tracking feeds a registry with explicit stage promotion. FastAPI serves the promoted model, and PSI and KS statistics compare live inputs with the training distribution.
Engineering decisions
A model bundle keeps the scaler and the feature view together with the model. Promotion archives the previous Production version, so serving stays traceable.
Tradeoffs
Drift statistics are cheap to compute. Choosing the alert threshold is the hard part, and drift is not the same as degradation.
Limitations
“Production” here is a registry stage name. The portfolio does not claim a running customer deployment.
Evaluation
Tests cover serving readiness, authentication, registry promotion and prediction monitoring. Seeded covariate shifts exercise the PSI and KS alerts.
What I would build next
Automated retraining triggers, once the thresholds are trustworthy.

Experimentation Toolkit

Run A/B tests that survive scrutiny — from power analysis to a ship-or-kill call.

A/B Testing · CUPED · Bootstrap · Stats
  1. Design + power

    sample_size_proportion, power_proportion and mde_proportion size a test before it runs.

  2. Assignment

    A seeded synthetic experiment: 24k users, a pre-period covariate and device-level effects.

  3. z / Welch / bootstrap

    A pooled two-proportion z-test, Welch’s t-test and a percentile bootstrap CI.

  4. CUPED + guardrails

    CUPED uses a pre-experiment covariate to tighten intervals. Guardrails must not regress. FDR correction controls false discoveries.

  5. Scorecard

    A SHIP, KILL or INCONCLUSIVE decision and a self-contained HTML scorecard.

01 / 05Design + power

sample_size_proportion, power_proportion and mde_proportion size a test before it runs.

Ritesh explains

Most A/B tests ship on noise. The toolkit sizes a test before it runs, and checks guardrails before it calls a win.

What it is
expkit: an end-to-end A/B analysis toolkit, from sample-size design to a ship, kill or keep-running decision.
How it works
Design the test, run a z-test, Welch t-test or bootstrap, apply CUPED variance reduction, check guardrails, correct for multiple comparisons, then decide.
Engineering decisions
Power and minimum detectable effect guide the design before any analysis. Guardrails and FDR control stop a nominal win from becoming a bad product decision.
Tradeoffs
A fixed-horizon test is simple and valid, but peeking at it early inflates false positives.
Limitations
The checkout experiment is synthetic. Its effect sizes are demonstration output, not commercial impact.
Evaluation
Tests cover the statistical helpers, CUPED, guardrails, multiple-comparison adjustment, decisions and scorecard generation on seeded data.
What I would build next
Sequential testing, so early stopping is statistically sound.
