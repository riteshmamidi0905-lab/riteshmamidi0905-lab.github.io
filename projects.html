FLAGSHIP BUILD / 02 · Data Engineering

Spark Data Lakehouse

End-to-end PySpark medallion (bronzesilvergold) lakehouse on 300K+ events: dedup, broadcast-join enrichment, partitioned Parquet marts, AQE tuning, data-quality checks.

PySparkParquetAQE
Architecture, decisions & limitations
Problem
Raw event data is duplicated, unenriched, and unqueryable — analysts can't trust or use it directly.
Architecture
Raw events Bronze Silver Gold marts BI / SQL
Approach
A layered medallion design isolates ingestion, cleaning/enrichment, and business marts, with data-quality checks between layers so bad data never reaches the gold tier.
Implemented result
Partitioned gold marts ready for BI, plus quality checks that fail loudly when inputs drift.
Evaluation
Unit tests cover cleaning, deterministic deduplication, enrichment, and gold aggregates. Data-quality rules inspect nulls, negative quantities and invalid enums.
Engineering decision
Small dimensions use broadcast joins; partitioned Parquet and AQE target avoidable shuffle and scan work.
Limitations
Local Spark and synthetic inputs demonstrate the processing architecture, not production scale.
What I learned
Deduplication belongs as early as possible. Next: automate the quality checks into a contract per layer.

FLAGSHIP BUILD / 01 · Data Engineering

Real-Time Streaming Pipeline

Kafka Spark Structured Streaming Cassandra fraud detection with event-time windows, watermarks, and a one-command Dockerized stack.

KafkaSparkCassandra
Architecture, decisions & limitations
Problem
Fraud signals decay in minutes; a nightly batch is far too slow to act on them.
Architecture
Synthetic events Kafka Fraud rules + windows Cassandra
Approach
Event-time processing with watermarks handles late and out-of-order events correctly, while a Dockerized stack makes the whole system reproducible with a single command.
Implemented result
Runnable Docker stack writing per-transaction verdicts and one-minute merchant metrics to Cassandra.
Evaluation
Pure Spark transforms are tested on static DataFrames: JSON parsing, fraud-rule decisions, and event-time merchant aggregations. A full Kafka/Cassandra runtime is a separate integration check.
Engineering decision
Explainable rules make each fraud flag inspectable. Event-time windows and watermarks bound late-data state; separate checkpoints track transaction and aggregate sinks.
Limitations
Synthetic transactions and rule-based detection; this is not a deployed payment-risk model.
What I learned
Checkpointing and Cassandra keys need to be reviewed together when assessing replay behavior. I would validate sink idempotency under failure and restart.

FLAGSHIP BUILD / 04 · GenAI · LLM

GenAI Document Assistant

Full-stack RAG with an extractive offline reader, source citations, arithmetic routing, SSE streaming, evaluation gates and configurable storage/generation backends.

RAGAgentsFastAPI
Architecture, decisions & limitations
Problem
General chatbots hallucinate and can't cite; teams need answers grounded in their own corpus.
Architecture
Query Retriever Relevant chunks LLM Cited answer
Approach
Retrieval-augmented generation grounds every answer in retrieved passages, a tool-using router-agent decides when to search vs. answer, and responses stream token-by-token.
Implemented result
A full-stack assistant that returns grounded, cited answers you can trace back to source.
Evaluation
A sample-corpus harness checks retrieval hit-rate, reciprocal rank, faithfulness and answer relevance, with CI thresholds. Tests cover retrieval, routing, streaming and API behavior.
Engineering decision
An offline extractive reader keeps the default path reproducible. Embedding, store and generation backends can be switched by configuration.
Limitations
Sample-corpus evaluation and local load testing are not evidence of performance across arbitrary documents or live users.
What I learned
The repository already blends vector similarity with keyword overlap. Next I would test retrieval failures across a broader corpus and measure abstention quality.

FLAGSHIP BUILD / 03 · GenAI · LLM

LLM Evaluation Framework

14 deterministic metrics, weighted JSON/YAML rubrics, hard gates, optional LLM judges, FastAPI, a CLI and an inspectable results dashboard.

LLM EvalJudgeAPI
Architecture, decisions & limitations
Problem
Teams ship LLM features without a repeatable way to measure whether answers are grounded or hallucinated.
Architecture
Test cases Model outputs Rubric judge Scores Dashboard
Approach
JSON/YAML rubrics define weighted criteria and hard thresholds. Deterministic metrics run offline; optional model judges score custom criteria through a vendor-neutral interface.
Implemented result
A reusable harness that turns 'it seems fine' into per-criterion faithfulness, hallucination, and refusal scores.
Evaluation
The repository includes an 18-case RAG-QA benchmark, deterministic scoring tests, threshold checks, API/report tests, and a CI fail-under option.
Engineering decision
Weighted rubric scores and hard thresholds are separate: a high overall score cannot override a required safety or grounding check.
Limitations
Token-overlap faithfulness is a heuristic. Optional LLM judges need calibration; neither proves factual reliability on its own.
What I learned
Judge calibration matters as much as the rubric. I'd add human-agreement tracking to trust the judge.

FLAGSHIP BUILD / 05 · MLOps

MLOps Platform

End-to-end ML platform: feature store, experiment tracking, model registry with stage promotion, FastAPI serving, and PSI/KS drift monitoring.

RegistryServingDrift
Architecture, decisions & limitations
Problem
Models get trained once and forgotten; nobody notices when live data drifts away from training data.
Architecture
Feature store Experiments Registry Serving Drift monitor
Approach
Experiment tracking feeds a model registry with explicit stage promotion, FastAPI serves the promoted model, and PSI/KS statistics continuously compare live inputs to the training distribution.
Implemented result
A local end-to-end lifecycle: train candidates, select and register a model, promote a version, serve predictions and inspect drift.
Evaluation
Tests cover serving readiness, authentication, registry promotion and prediction monitoring. Seeded covariate shifts exercise PSI/KS drift alerts.
Engineering decision
A model bundle keeps the scaler and feature view with the model. Registry promotion archives the previous Production version for traceable serving.
Limitations
Production is a registry stage name; the portfolio does not claim a running customer deployment. Drift indicates distribution change, not automatically model degradation.
What I learned
Drift detection is easy; deciding the alert threshold is hard. Next: automated retraining triggers.

FLAGSHIP BUILD / 06 · Analytics

Experimentation Toolkit

End-to-end A/B analysis: power &amp; sample-size design, z-test/Welch/bootstrap, CUPED variance reduction, guardrails, FDR, and a ship-or-kill scorecard.

A/BCUPEDStats
Architecture, decisions & limitations
Problem
Naïve A/B tests ship on noise — no power analysis, no variance reduction, no multiple-comparison control.
Architecture
Design + power Assignment z / Welch / bootstrap CUPED + guardrails Scorecard
Approach
The toolkit covers the full lifecycle: sample-size design up front, robust test statistics, CUPED to cut variance, guardrail metrics, and FDR control before a ship-or-kill scorecard.
Implemented result
An end-to-end analysis that turns a raw experiment into a defensible decision.
Evaluation
Tests cover statistical helpers, CUPED, guardrails, multiple-comparison adjustments, decisions and scorecard generation on seeded data.
Engineering decision
Power and minimum detectable effect guide design before analysis. Guardrails and FDR help prevent a nominal win from becoming a bad product decision.
Limitations
The checkout experiment is synthetic. Its effect sizes are demonstration output, not commercial impact.
What I learned
Guardrails catch the wins that quietly break something else. Next: sequential testing for early stopping.
