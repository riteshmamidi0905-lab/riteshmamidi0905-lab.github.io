Flagship build 03

LLM Evaluation Framework

14 deterministic metrics, weighted JSON/YAML rubrics, hard gates, optional LLM judges, FastAPI, a CLI and an inspectable results dashboard.

  • LLM Eval
  • Judge
  • API
Architecture, decisions & limitations

ProblemTeams ship LLM features without a repeatable way to measure whether answers are grounded or hallucinated.ArchitectureTest cases Model outputs Rubric judge Scores DashboardApproachJSON/YAML rubrics define weighted criteria and hard thresholds. Deterministic metrics run offline; optional model judges score custom criteria through a vendor-neutral interface.Implemented resultA reusable harness that turns 'it seems fine' into per-criterion faithfulness, hallucination, and refusal scores.EvaluationThe repository includes an 18-case RAG-QA benchmark, deterministic scoring tests, threshold checks, API/report tests, and a CI fail-under option.Engineering decisionWeighted rubric scores and hard thresholds are separate: a high overall score cannot override a required safety or grounding check.LimitationsToken-overlap faithfulness is a heuristic. Optional LLM judges need calibration; neither proves factual reliability on its own.What I learnedJudge calibration matters as much as the rubric. I'd add human-agreement tracking to trust the judge.

Architecture, decisions & limitations

ProblemFraud signals decay in minutes; a nightly batch is far too slow to act on them.ArchitectureSynthetic events Kafka Fraud rules + windows CassandraApproachEvent-time processing with watermarks handles late and out-of-order events correctly, while a Dockerized stack makes the whole system reproducible with a single command.Implemented resultRunnable Docker stack writing per-transaction verdicts and one-minute merchant metrics to Cassandra.EvaluationPure Spark transforms are tested on static DataFrames: JSON parsing, fraud-rule decisions, and event-time merchant aggregations. A full Kafka/Cassandra runtime is a separate integration check.Engineering decisionExplainable rules make each fraud flag inspectable. Event-time windows and watermarks bound late-data state; separate checkpoints track transaction and aggregate sinks.LimitationsSynthetic transactions and rule-based detection; this is not a deployed payment-risk model.What I learnedCheckpointing and Cassandra keys need to be reviewed together when assessing replay behavior. I would validate sink idempotency under failure and restart.
