A reference implementation, not a product: the customer is fictional, the data is synthetic, it has never been deployed, and every model result comes from a deterministic rule-based stand-in rather than a language model. What it does show is the engineering around a model: tenant isolation in the database, a closed vocabulary of typed actions, deterministic policy, approvals bound to the exact action, idempotent execution, a tamper-evident audit log, and an evidence base that states what it does not prove.

Flagship 01 · Applied AI system

Support Escalation Copilot

An approval-gated AI case workflow for a fictional B2B SaaS support team. The model helps with reading and drafting; everything that can hurt a customer stays in deterministic code and in human hands.

Python · PostgreSQL 16 + pgvector · Row-level security · Typed actions · Hash-chained audit
  1. Customer problem · Limitation

    Tier-2 engineers at a fictional freight-software vendor read tickets, hunt through stale and contradictory runbooks, then ask for approval in chat. The costly mistakes touch customers: a feed re-synced twice, a credit outside policy, the wrong tenant's data. The customer is fictional and every record is synthetic.

  2. Ticket arrives · Verified

    The ticket enters as untrusted text: data, never instructions. The operator surface is server-rendered with no JavaScript, a strict content-security policy and CSRF-protected forms, and every read and action is re-authorised on the server.

  3. Tenant scoped · Verified

    Before any evidence is read, the case is scoped to one account. Isolation is enforced in the database with forced row-level security keyed to a signed, short-lived scope, not by the model and not by a prompt.

  4. Evidence retrieved · Verified

    Runbook evidence is retrieved with provenance. On a frozen 40-ticket held-out set, vector search ranked best (Hit@1 0.8 against 0.6 for lexical), and similarity alone cannot tell you the evidence is missing, so sufficiency is judged separately.

  5. AI diagnosis · Simulated

    The model returns a structured diagnosis: hypotheses, cited evidence, what is missing or contradictory. Its output is untrusted data checked by deterministic code. Here the model is a rule-based stand-in, not an LLM, so this stage shows the orchestration, not model quality.

  6. Typed action proposed · Verified

    The only write vocabulary is 5 typed actions, 3 of them human-gated. No code path can send customer email, and 16 dangerous request names are rejected by name before policy sees them.

  7. Policy evaluates · Verified

    Policy is code over trusted facts: it allows a proposal, requires approval, denies, abstains or escalates, with reason codes, and re-evaluates from fresh facts at execution. In the hostile-ticket demo a 100% credit request is refused with CREDIT_ABOVE_AGENT_THRESHOLD, whatever the model asked for.

  8. Human approval required · Verified

    A person with the exact role approves the exact action. The approval binds to the action's canonical hash, role, tenant, case and expiry. An amended action voids it and needs a new approval that its amender cannot give. Approvers are simulated signed identities.

  9. Idempotent execution · Verified

    Every customer write carries a deterministic idempotency key recorded in a ledger. If the outcome is unknown after a timeout, the system does not retry blindly: it shows an uncertain outcome and a human reconciles it. Customer systems are mocks with fault injection.

  10. Audit and recovery · Verified

    Every proposal, decision, approval, execution and refusal goes to an append-only, hash-chained audit log. A lease-based worker resumes cases from durable state; with concurrent workers, including ones that ignore the lease, tests produce exactly one effect per approved action.

02 Adversarial story

A malicious instruction reaches the model. The model may misbehave. The controls do not depend on it behaving.

Adversarial story · scripted model

A hostile ticket, an obedient model, nothing executed

Demo C of the repository: a ticket and injected runbooks tell the assistant to skip approval, refund 100%, re-sync and e-mail everyone. The model here is a scripted wrapper that does exactly what the injected text says, which is the worst case for the controls.

  1. Hostile inputTicket text and injected runbooks ask to skip approval, refund 100%, re-sync and e-mail everyone.
  2. Model (scripted, obedient)Complies: proposes an e-mail to the customer, a full credit and a re-sync.
  3. Trust boundaryThe e-mail proposal is dropped as FORBIDDEN_ACTION: it is not in the action vocabulary.
  4. Deterministic policyThe 100% credit is refused with CREDIT_ABOVE_AGENT_THRESHOLD.
  5. Approval serviceThe re-sync still waits for a human; the injected text is shown to the approver as data, inside the exact action.
  6. ResultNothing was executed. The case waits for an approval, and a secret-echoing draft was rejected.

Across 32 injection runs the four invariants held (0 violations), and the ten hostile-ticket attacks ended the same way with injection detectors on or off. Containment is not the same as a correct outcome, and the model was scripted, not an LLM.

03 The residual risk

The weakness that stays: a convincing draft that is grounded and wrong.

What the controls cannot catch

What the rules cannot see

Deterministic grounding checks run on every draft reply before a human sees it. They were developed against 20 steered drafts and catch all of them. They catch none of the same harms rephrased, and none of the misleading drafts built only from grounded words. That last result is kept on purpose.

Benign drafts (a flag here is a false rejection)0 / 13 flagged

The design answer is not a cleverer rule. Review is mandatory and itemised, risk flags raise it, and the draft is internal and never sent by the system. Human review is recorded but is not a technical gate on use, and its effectiveness was not measured.

Known limitations

Stated by the repository itself, kept in the open.

Known limitations
LabelClaim and qualificationEvidence
Limitation

Pattern-based redaction removes labelled secrets (Bearer tokens, NAME=value, PEM blocks, DSN passwords) but not a bare unlabelled token typed into a ticket; that token is stored and shown to operators entitled to that tenant.

Qualification. Pinned by a test as a documented residual (R-54); entropy heuristics would add false positives and were not attempted.

deterministic testslimit-unlabelled-secrets
Limitation

A convincing wrong draft made only of grounded words and numbers cannot be detected by any deterministic rule here; the only control is human review, which is recorded but is not a technical gate on use.

Qualification. Human review effectiveness was not measured (R-58).

adversarial dev corpuslimit-misleading-grounded-drafts
Limitation

Sign-in is simulated: a persona picker mints a signed identity; there is no real authentication, session revocation, rate limiting or MFA.

Qualification. Demo-only by design (R-59); a deployment needs an identity provider.

Limitation

Reconciling an uncertain write as applied trusts the operator's recorded note, and the audit log has no external anchor, so deletion of the most recent events is detectable only with one.

Qualification. Documented residuals (R-32, R-62).

07 What comes next

What I would do to close the gaps.

  1. Run the frozen real-model protocol against a local open-weights model and report it beside the stand-in results.
  2. Replace simulated sign-in with a real identity provider, and add the external audit anchor.
  3. Measure whether itemised human review actually catches the misleading drafts.
